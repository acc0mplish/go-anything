# 강화 루프 (hardening loop)

목표: 원본 프로그램의 동작을 기준으로 재작성을 반복해서 검사하고 고쳐, 기록에 없던 차이를 줄인다.
원본 코드는 수정하지 않는다. 원본의 결함은 발견해서 보고하고, 기록은 원본의 실제 동작을 그대로 남긴다.

## 한 라운드 (round)

1. 점검 요청: 새 시드로 입력을 만든다 (`domain.ProbeValues`, `domain.FuzzInputs`, `wire refine`의 점검 요청).
   시드는 로그에 남겨서 같은 라운드를 다시 돌릴 수 있게 한다.
2. 비교: 원본과 재작성에 같은 입력을 넣고 응답을 비교한다.
3. 분류: 차이가 난 입력마다 하나로 분류한다.
   - 재작성 결함: 원본의 응답이 맞다고 보고 재작성을 고친다.
   - 원본 결함: 원본이 패닉하거나, 같은 입력에 다른 응답을 하거나, 명백히 잘못된 응답을 한다.
     기본값은 원본 동작을 보존하는 것이다. 원본 결함은 근거와 함께 보고서에 적는다.
   - 판정 보류: 기록에만 남기고 다음 라운드에서 다시 본다.
4. 기록: 원본의 응답을 정답으로 기록에 추가한다. 기존 기록은 바꾸지 않는다. 이름 충돌은 피한다.
5. 수정: 재작성 결함만 고친다. 기록으로 테스트를 다시 만든다.
6. 게이트: `go-anything gate`(gofmt, vet, build, test, 미구현 검사, unsafe 검사)와 기록 재생을 통과해야 한다.

## 멈추는 조건

- 두 라운드 연속으로 새 시드에서 차이가 0이면 일치 완료로 본다.
- 세 라운드 연속 진전이 없으면 멈추고 남은 차이를 보고한다.
- 라운드 수 한도(기본 4)를 넘으면 멈춘다.

## 게이트 원칙

- 원본을 실행하는 입력은 원본 프로그램이 이미 허용하는 범위로 제한한다.
- 원본이 패닉하는 입력은 기록하되 회귀 기준으로 쓰지 않고 결함으로 따로 적는다.
- 퍼즈 실패 입력은 `testdata`로 남기고 회귀 테스트로 고정한다.

## 한계

- 루프는 샘플링이다. 생성되지 않은 입력의 차이는 찾지 못한다.
- 원본의 의도와 다른 동작을 원본 결함인지 재작성 결함인지 자동으로 판정할 수 없다. 기본 규칙은 원본 보존이다.
- 입력 생성기의 범위가 곧 루프의 범위다.

## 첫 라운드 기록 (자기 파서 대상)

- 대상: 외부 입력을 받는 파서 7개와 MCP 서버 1개의 Go 네이티브 퍼즈 (`FuzzParseCoverProfile`, `FuzzParseTop`,
  `FuzzParseGoTestJSON`, `FuzzGoVersionAtLeast`, `FuzzScanUnsafe`, `FuzzScanUnimplemented`, `FuzzPortPlan`, `FuzzServe`).
- 실행: 대상별 15초, 각 대상 약 50만 회 이상 실행.
- 결과: 패닉과 잘못된 결과는 없었다. 이 라운드는 원본과 재작성 쌍이 아니므로 기준선일 뿐이다.

## 두 번째 라운드 (원본과 재작성 쌍, orders CLI)

- 원본: 파이썬 CLI. 의도적 결함을 하나 넣었다. 앞자리 0이 있는 id(`007`, `00`)에서 호출 스택을 출력하며 죽는다.
  위첨자 숫자(`²`, `³`)도 같은 방식으로 죽는다.
- 1라운드: 재작성 자리표시자가 58개 점검 요청에서 실패. 30건을 기록하고 원본 크래시 2건을 결함으로 분리했다.
  같은 라운드의 결함 중복은 도구 버그였고 고쳤다(중복 표를 라운드마다 새로 만들고 있었다).
- 2라운드: 에이전트가 재작성을 고친 뒤 60개 점검 요청이 모두 일치. 일치 완료.
- 점검 요청 밖 검사: 원본이 받아들이는 유니코드 숫자(`٣`, `१२`)를 재작성이 거부했다. 점검 요청 생성기에 비ASCII 숫자가
  없었던 것이 빈틈이었다. 생성기에 추가하고 다시 돌려서 4건을 기록, 에이전트가 고쳐 일치 완료.
  기본 규칙(원본 보존)에 따라 재작성 결함으로 분류했다. 원본이 이 입력을 받아들이는 것은 파이썬의 `isdigit`/`int`가
  우연히 그렇게 되는 것이므로, 원본 결함으로 옮기고 싶다면 운영자가 결정할 수 있다.
- 최종 검증: 점검 요청 밖 입력 19개에서 원본과 재작성 일치. 원본 크래시 3개는 결함으로 분리.
- 교훈: 점검 요청 생성기가 입력 범위를 결정한다. 빈틈은 라이브 비교로만 드러났다.

## 다음 라운드 대상

- 원본이 허용하는 입력 범위를 생성기에 명시적으로 넣는 방법(문자 클래스별 점검 요청) 검토.
- HTTP 쌍을 같은 방식으로 돌리기.
