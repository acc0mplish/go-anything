## 비결정성 정규화, rust-anything normalize 대응 (최신)

- `CompareOptions.Normalize`를 추가했다. `-normalize timestamps`, `-normalize uuids`, `-normalize name=regex`를 반복 가능한 플래그로 `verify`, `app replay`, `wire gen`, `wire verify`, `wire refine`에 붙였다. 비교 전 양쪽에서 해당 값을 마스크하므로 시각 차이와 새 UUID가 일치로 판정된다. 에포크 정수는 의도적으로 마스크하지 않는다(데이터인지 시계인지 구분 불가).
- `EqualBody`와 stderr 비교가 같은 정규화를 쓴다. 이 파일이 유닛에 복사되므로 생성 테스트와 도구가 같은 규칙으로 판정한다(회귀 테이프 `TestGeneratedTestUsesTheNormalizersItWasGivenLikeTheTool`).
- 복사기 결함 수정. 최상위 함수와 같은 이름의 구조체 필드(`Normalize` 필드 대 `Normalize` 함수)가 접두사 처리되어 생성 테스트가 컴파일되지 않았다. 필드명, 리터럴 키, 셀렉터는 접두사를 붙이지 않게 고쳤다(`TestComparisonCopyKeepsFieldAndSelectorNames`).

rust-anything 대비 남은 것. `pin_clock`(원본 런타임에 시계/난수 몽키패치)은 go-anything의 원본이 임의 프로그램이라 적용하지 않고 마스킹과 `-repeat` 불안정 감지로 대응한다. `fresh`(작업 디렉터리 스냅샷 격리)와 `pace`(응답 후 대기)는 미구현, 후보로 남긴다.

## HTML 보고서 보강

세 보고서가 같은 스타일(`domain.ReportCSS`)을 쓰고, 판정과 다음 단계를 맨 위에 둔다. 스크립트와 외부 자원은 없다. 기록값은 `domain.ClipForReport`로 2048바이트에서 자르고, 개인정보가 들어 있을 수 있다고 footer에 적는다.

| 보고서 | 위치 | 바뀐 점 |
|---|---|---|
| 검증 (`verify`, `app replay` + `-report x.html`) | 지정한 파일 | 판정 배너와 다음 단계, 실행 정보(재작성 명령, 기록 파일, 시각, 버전), 필드별 실패 수, 불일치마다 **입력값**, 다른 부분 표시와 보이는 공백, 일치 케이스는 접기. 요청 헤더는 입력에서 빼고, 명령의 토큰과 비밀번호 인자는 가린다. |
| 분석 (`analyze`) | `.go-anything/reports/<module>/vN/` | 요약 배너(무엇부터, 무엇을 조심), 모듈 기준 상대 경로, wave별 묶음과 readiness 막대, 위험 종류별 설명, **이전 버전과의 차이**. 비교를 위해 버전마다 `analysis.json`을 저장한다. |
| RSI 루프 (`wire refine`, 새로 생김) | `.go-anything/checks/<unit>/index.html` | 회차마다 다시 쓴다. 수렴 여부, 회차별 불일치 추이, 입력 클래스, 원본 결함, RBAC, 확인하지 않은 것. |

판정이 과장되지 않도록 고친 것:
- 한 회차만 돈 실행을 "Converged"라고 쓰던 것을 "1 clean round, not yet converged"로 바꿨다. 터미널 출력, 페이지 배너, 회차 배지 모두 같다. 종료 코드는 그대로 0이다.
- 수렴했어도 시험하지 않은 입력 클래스가 있으면 배너를 초록이 아닌 주황으로 낮추고, 빠진 클래스와 `-probes`를 늘리라는 다음 단계를 쓴다. `-probes 10`에서는 주황, `-probes 60`에서는 초록을 실제 실행으로 확인했다.
- 회차 기록에 `defect_policy`를 남긴다. 원본 결함 설명이 실행의 실제 정책을 따른다.
- 분석 카드의 변화량 0은 "no change"로 쓴다.

확인한 방법: 각 보고서를 실제 바이너리 실행으로 만들고 헤드리스 Chromium으로 화면을 찍어 직접 봤다. 기록값에 `<script>`가 있어도 태그로 나오지 않는 것을 테스트로 확인했다.

한계:
- 차이 표시는 공통 앞부분과 뒷부분만 빼므로, 떨어진 두 곳이 다르면 그 사이 전체가 표시된다.
- RSI 페이지는 수정 시각으로 이전 실행의 회차 기록을 구분한다. 같은 시각에 겹친 실행은 구분하지 못한다.
- 업그레이드 전 분석 버전에는 `analysis.json`이 없어서, 업그레이드 후 첫 분석은 비교 없이 나온다.
- 좁은 화면과 인쇄 화면은 확인하지 않았다.

## rust-anything 대비 남은 네 항목 구현

Rust 설계를 옮기지 않고 Go 표준 도구로 만들었다. 새 모듈 의존성은 없다. 네 기능 모두 빌드한 바이너리로 실행해 확인했다.

| rust-anything | go-anything | Go 방식 | 실행 확인 |
|---|---|---|---|
| Generate shadow module | `shadow gen` | `go/types`로 원본 패키지의 공개 함수 시그니처를 읽고, 같은 API의 Go 패키지를 생성한다. `GA_SHADOW_<PKG>=old\|shadow\|new`를 호출마다 읽는다. | 섀도 모드에서 원본 값을 돌려주고 다른 결과 한 건만 JSON으로 기록 |
| Lay out packages | `package` | PyO3, napi 대신 `go install`, `CGO_ENABLED=0` 크로스 빌드, 태그 릴리스 워크플로, SHA256SUMS를 생성한다. `-check`는 한 머신에서 모든 타깃을 실제로 빌드한다. | go-anything 자체를 linux/arm64, windows/amd64로 빌드 성공 (12초) |
| Scaffold Rust front door | `frontdoor scaffold` | axum, clap 대신 표준 라이브러리 `httputil.ReverseProxy`와 `os/exec`로 `<repo>/go/app`을 만든다. `wire gen`이 그대로 유닛을 마운트할 수 있는 형태다. | 골격 3/3 통과(전부 폴백), 유닛 마운트 후 빌드와 재생 3/3, 종료 후 포트와 원본 프로세스 정리 |
| Analyze (깊이) | `analyze` | `go/types`로 타입 검사, 정적 호출 그래프, 함수 단위 start_here, file:line 위험 | go-anything 자체에서 함수 509, 정적 호출 708, 동적 호출 195, 위험 7 |

함께 고친 것:
- `version`을 `var`로 바꿨다. 릴리스 빌드에서 `-ldflags "-X main.version=..."`가 적용된다.
- `analyze`의 안내문을 표준 오류로 옮겼다. 표준 출력은 JSON 하나라서 파이프로 쓸 수 있다.
- `/dist/`를 `.gitignore`에 넣었다.
- 게이트 검사와 `wire gen`의 빌드 확인이 출력 경로 없이 `go build ./...`를 실행했다. 대상이 main 패키지 하나면 Go가 그 폴더에 바이너리를 쓴다. 저장소 안에 29MB 바이너리가 반복해서 생긴 원인이었다. 두 곳 모두 임시 폴더로 빌드하게 고쳤고, 옛 동작에서 실패하는 테스트를 추가했다.

한계:
- `shadow gen`은 결과만 비교한다. 인자를 바꾸는 함수는 두 번 실행되므로 위험 목록에 나온다. 메서드와 제네릭 함수는 섀도하지 않는다.
- `analyze`는 인터페이스와 함수 값 호출을 풀지 못하고 개수로만 센다. 실행 시간은 약 2배(약 3.6초), 메모리는 약 13배(약 240MB)로 늘었다.
- `frontdoor scaffold`는 종료할 때 처리 중인 요청을 끊는다. Linux 밖에서는 프런트 도어를 강제 종료하면 원본이 남을 수 있다.
- 생성한 릴리스 워크플로는 GitHub에서 실행해 보지 않았다.
- `wire gen`의 안내문은 골격 앱에도 `GA_ORIGINAL_URL`을 직접 주라고 한다. 골격은 이 값을 스스로 설정하므로 안내가 정확하지 않다.

## 실제 앱 시험: KLIC-Chatting

Rust(Axum, SeaORM) 팀 채팅 앱을 로컬 PostgreSQL 17 컨테이너와 빌드된 서버로 띄워 `go-anything rbac`로 검사했다. 테스트 데이터는 실행마다 새로 만들었고, 실행 뒤 서버와 컨테이너를 종료하고 제거했다. 원본 저장소에는 파일을 쓰지 않았다.

관찰된 결과 (실제 응답, 자기 보고 아님):
- 익명 요청으로 `GET /api/v1/users`와 `GET /api/v1/users/{id}`가 200을 돌려준다. 레코드에 `email` 필드가 있다.
- 다른 테넌트 사용자(팀 B 관리자)가 팀 A 사용자 프로필을 200으로 읽는다.
- 팀 멤버(`team_user`)가 팀 이름 변경(PUT), 멤버 추가(POST), 관리자 제거(DELETE), 팀 삭제(DELETE)를 모두 성공시킨다. `team_admin` 역할은 저장만 되고 검사되지 않는다.
- 팀 멤버(`team_user`)가 채널을 삭제한다(204).
- 채널 관리자가 다른 팀 사용자를 채널에 추가한다(201). 추가 대상이 팀 소속인지 검사하지 않는다.
- 팀/채널/게시글 읽기는 다른 테넌트에 거부된다(404 또는 403). 게시글 수정과 삭제는 코드상 작성자만 허용한다(이 시험에서는 검사하지 않음).
- 속도 제한 키가 클라이언트가 보내는 `X-Forwarded-For`다. 같은 헤더로 61번째부터 429, 헤더를 바꾸면 70번 모두 통과한다.

정책의 전제 (추정, 운영자 확인 필요): 팀 설정 변경, 멤버 관리, 팀과 채널 삭제는 `team_admin`만 해야 한다고 가정했다. 근거는 DB 스키마의 `team_admin` 역할이 존재한다는 점뿐이다. 채널 추가 대상은 같은 팀 멤버여야 한다고 가정했다.

이 시험에서 고친 go-anything 결함 두 가지:
- RBAC 요청이 케이스의 다른 헤더를 지웠다. 이제 보존하고, 케이스가 가진 Authorization은 제거한다(익명 요청이 실제로 익명이 되도록).
- `app record`와 `replay`가 JSON 본문에 Content-Type을 붙이지 않았다. axum 같은 서버는 415로 거부한다. 유효한 JSON 본문에 명시된 타입이 없으면 `application/json`을 붙인다. 이전에 기록한 `app.json` 중 JSON POST 결과가 415인 것은 다시 기록해야 한다.

알려진 한계:
- 정책 모델은 역할과 테넌트만 본다. "작성자만 수정"처럼 사용자별 소유 규칙은 표현할 수 없다.
- 시험은 단일 요청 판정이다. 상태 기반 흐름은 보지 않는다.
- `rbac -v`로 셀 단위 결과를 출력할 수 있다.

## 권한(RBAC) 구조 검사 (최신)

`go-anything rbac`는 케이스마다 역할과 테넌트별 호출자로 요청을 보내고, 허용과 거부만 비교한다. 응답 본문은 보지 않는다.
세 가지를 확인한다.

1. **명세 대조**: 선언된 정책(`allowed_roles`, `owner_tenant`, `cross_tenant_roles`, `public`)과 관찰이 다르면 치명적이다.
2. **원본 대조**: `-original`을 주면 원본과 재작성의 허용·거부가 다를 때 치명적이다.
3. **서버 오류**: 권한 응답 자리에 5xx가 나오면 높음으로 보고한다. 5xx를 거부로 세지 않는다.

확인한 것(실제 바이너리, 살아 있는 서버 두 개):
- 올바른 재작성은 0건, 종료 0.
- 테넌트 누수 재작성은 `clerk-globex`가 다른 테넌트 송장을 받는 것을 두 가지 치명적 결과로 보고, 종료 1.
- 토큰 환경변수가 없으면 검사가 중단된다. 통과하지 않는다. 표준 오류에 변수 이름만 나온다. 토큰 값은 출력되지 않는다.
- 정책이 없는 케이스는 출력에 목록으로 남아 사람의 검토를 요구한다.

한계와 열린 결정:
- 정책 파일은 사람이 쓴다. 정책이 빠진 보호 대상 엔드포인트는 이 도구가 찾아내지 못한다. 목록으로만 드러난다.
- 본문에 든 다른 테넌트의 데이터는 검사하지 않는다. 허용된 요청이 다른 테넌트의 데이터를 담아도 허용으로만 센다.
- 기본 규칙은 권한에 대해 "원본 보존"을 적용하지 않는다. 원본이 잘못 허용하면 그것도 치명적으로 보고한다.
  원본의 권한 결함을 기록으로 고정하는 것은 어떤 정책으로도 허용하지 않는다.
- 단일 요청에 대한 판정이다. 여러 요청에 걸친 상태 기반 권한(예: 승인 흐름)은 검사하지 않는다.

## 수정 반영 (이전)

- **입력 클래스**: 프로브 값마다 클래스가 하나 있다(`empty`, `padded`, `signed`, `overflow`, `leading-zero`,
  `ascii-digits`, `unicode-digit`, `numeric-symbol`, `non-numeric`). 회차 기록에 `value_classes`와 `missing_classes`가 생긴다.
  에이전트 검토에서 찾은 빈틈은 고쳤다. 유니코드 0으로 시작하는 값(`٠١`, `０１`)은 `leading-zero`다.
- **원본 크래시 정책**: `wire refine -defect-policy defect|expected`. 기본은 `defect`(결함으로 보고, 기록하지 않음).
  `expected`는 크래시를 기대 동작으로 기록한다. 잘못된 값은 허용 값과 함께 거부된다.
  - 한계: `expected`에서도 비교는 stderr까지 맞춰야 한다. 재작성이 트레이스백 글자까지 똑같이 내야 하므로 실용성이 낮다.
    종료 코드만 비교하는 방식은 아직 없다. 열린 결정이다.
  - 위험: 크래시 본문이 기록 파일에 들어간다. 민감 정보가 있을 수 있으므로 기록 전 마스킹이 필요한지 정해야 한다.

## 병렬 작업과 HTTP 쌍 회차

- `.gitignore`에 `.go-anything/`을 추가했다. 회차 기록과 보고서가 커밋되지 않는다.
- 레지스트리 테스트(`commands_test.go`): 레지스트리의 CLI 명령이 실제 디스패치에 있는지 확인한다. 불일치를 넣으면 실패한다
  (변조 검사로 확인). `commands`를 레지스트리에 추가했다.
- 결함 중복 방지를 `usecase.DefectLog`로 뺐다. 이전 테스트는 라운드 2에 도달하지 못해서 중복 방지를 검증하지 못했다.
  이제 로그 단위 테스트가 검증하고, 통합 테스트는 "한 라운드에서 한 번"만 주장한다.
- 오래된 `.defects.json`이 결함 없는 실행 뒤에도 남던 문제를 고쳤다. 결함이 없으면 파일을 지운다.
- HTTP 쌍(`orders`, 원본 결함은 앞자리 0 `007`)을 실제 에이전트로 돌렸다. 2회차에 수렴했다. 결함 1건을 한 번 기록했다.
  프로브 밖 확인에서 `/orders/00`도 원본이 죽는 것을 찾았다. 프로브 집합에 없어서 결함 목록에 빠져 있었다.
  앞자리 0 결함은 지금 `007`로만 대표된다.

## craft-anything에서 적용한 것

1. **회차마다 확인 기록**: `wire refine`은 회차마다 `.go-anything/checks/<unit>/round-NN.json`을 쓴다.
   시드, 경계값과 생성값의 수, 요청 수, 불일치 수, 새 케이스, 원본 결함 수, 수렴 여부, 에이전트 결과를 담는다.
   모든 기록에 "확인하지 못한 범위"와 신뢰 범위를 함께 적는다. 깨끗한 회차는 "샘플링한 입력에서 일치"만 뜻한다.
2. **도구 목록 한 곳**: `go-anything commands`가 명령마다 MCP 노출 여부와 이유를 보여 준다. 테스트는 MCP에
   노출된 도구가 모두 목록에 있는지 확인한다.

적용하지 않은 것과 이유:
- 클린룸 강제 모드: 우리 도구는 원본을 처음부터 블랙박스로 다룬다. 원본 소스는 `-src` 지문 계산에서만 읽는다.
  별도 모드를 만들기 전에 실제로 원본 코드를 읽는 경로가 어디인지 먼저 정해야 한다.
- 명령 실행 전 승인 카드: `wire refine -agent`와 `wire verify`는 이미 사용자가 명령을 직접 지정한다. 대화형 승인은
  MCP 호출자가 응답할 수 없으므로 맞지 않는다.
- 두 단계 UX(간단 모드, 고급 모드): 명령줄은 이미 짧은 명령과 플래그로 나뉘어 있다. 추가 모드는 중복이다.

## 섀도, 포팅 순서, lift MCP 노출

1. **섀도 모드**: 레지스트리에 `GA_UNIT_<NAME>=shadow`가 추가됐다. 원본 응답을 호출자에게 돌려주고,
   재작성도 같은 요청으로 실행해 다르면 로그에 남긴다. 재작성이 패닉해도 호출자 응답은 원본이다.
   - 실행 확인: CLI에서 같으면 조용하고 다르면 로그, HTTP에서 호출자는 원본 본문을 받고 서버 로그에 차이가 남는다.
2. **포팅 순서와 준비도**: `analyze`의 JSON(`port_order`), HTML 보고서, MCP 결과에 패키지별 순서, 단계(wave),
   준비도(0~100), 위험 사유가 나온다. 테스트 파일 수를 분석에 넣었다. 단계는 내부 임포트 깊이, 준비도는
   `unsafe`/cgo(-25), 외부 부작용(-10), 리플렉션(-5), 테스트 없음(-20), 넓은 API(-10).
   - 실행 확인: 이 저장소에서 의존 없는 패키지가 앞에 오고 `os/exec`를 쓰는 `subject`는 감점된다.
3. **lift MCP 노출**: 앱 재생, 게이트(기본 테스트 생략), 단위 기록의 드리프트만 본다. 단위 명령은 실행하지 않는다.
   결과에 "단위 동작은 여기서 실행하지 않았다"고 적는다. 원본과 재작성 주소가 같으면 거부한다.
- MCP 서버는 도구가 오류를 낼 때 보고 본문을 함께 보낸다. 이전에는 실패 사유가 버려졌다.
- 섀도 모드는 생성된 레지스트리에 들어간다. 단위별 파일을 따로 만들지는 않는다.

## MCP 도구 확장 (이전)

`record`, `bench`, `app_record`를 추가해 MCP에서 11개 도구를 노출한다. 이후 `lift`를 더해 12개다.
노출하지 않은 것은 `lift`, `wire verify`, `wire refine`, `profile`이다. 빌드·프로그램 실행 또는 에이전트 셸 명령을
수행하므로 MCP 호출자에게 열지 않았다. `bench`는 출력이 다르면 오류를 반환해 잘못된 속도를 보고하지 않는다.

## 이번 라운드 (rust-anything 비교 1~5번)

1. **요청 헤더**: 앱 케이스에 `request_headers`를 쓸 수 있다. 값에 `${NAME}`을 쓰면 실행 시점에 환경변수에서 읽고,
   기록 파일에는 자리표시자만 남는다. 변수가 없으면 요청을 보내지 않고 오류가 난다.
   - 테스트: 헤더 전달, 환경변수 치환, 변수 없음 오류, 기록에 비밀이 남지 않음.
2. **MCP 도구 확장**: `analyze`, `verify`에 더해 `gate`, `app_replay`, `fuzz`, `doctor`, `map`, `wire_status`를 노출한다(총 8개).
   명령줄과 같은 코드를 호출한다. 목록과 호출을 테스트한다.
3. **record 자동 경계값**: `record -edges N [-edge-seed S]`가 경계값과 생성 입력을 N개 더한다. 같은 시드는 같은 입력.
4. **wire 재생 자동화**: `wire verify <모듈> <unit> [prefix] -cases app.json (-original-cli|-original-url)`.
   모듈을 빌드하고 이 단위만 재작성으로 보내며, CLI는 바이너리를 직접 실행하고 HTTP는 `main.go`의 리슨 주소(리터럴)로 앱을 띄워
   기록 케이스를 재생한 뒤 끈다. 실제 실행: 정답 PASS, 본문/출력이 틀리면 FAIL로 차이를 지목(HTTP·CLI 모두).
5. **메일 효과**: `-mail 127.0.0.1:<port>`로 루프백 SMTP 수신기를 띄워 앱이 보낸 메일의 발신자·수신자·본문을 기록한다.
   `Date`와 `Message-ID`는 비교에서 뺀다. 실제 실행: 같은 메일 PASS, 본문만 바뀐 메일 FAIL.

### 한계
- 요청 헤더 값을 그대로 쓰면(`${}` 없이) 기록 파일에 비밀이 평문으로 남는다. `${NAME}` 사용을 권장한다.
- MCP는 8개만 노출한다. `record`, `wire gen`, `wire refine`, `lift`, `app_record`, `profile`, `shadow` 생성, `package`는 아직 없다.
- `wire verify`는 모듈 루트의 `main` 패키지만 빌드한다. HTTP 리슨 주소는 문자열 리터럴이어야 한다.
  다른 단위는 원본으로 가므로 `-original-*`이 가리키는 원본이 떠 있어야 한다.
- 메일 수신기는 평문 SMTP만 받는다(TLS, AUTH 없음). 앱이 이 수신기를 쓰도록 설정해야 한다.
- `record -edges`는 표준입력 기반 `record`에만 있다. HTTP 단위의 경계값은 `wire refine` 프로브가 맡는다.

## 이번 라운드에서 구현하고 실행으로 확인한 것 (rust-anything 대조 1~6번)

1. **비결정성 검사**: `app record`는 케이스를 기본 2회 실행하고, 실행마다 달라지는 필드(본문, 헤더, 상태, 효과 등)를
   `unstable`로 표시한다. 재생은 그 필드만 건너뛰고 나머지는 계속 비교한다. `-strict`면 불안정 케이스가 있을 때 기록 실패.
   - 실서버 확인: 시각 값 본문은 불안정 처리되어 PASS, 고정 응답이 바뀌면 FAIL.
2. **gate**: gofmt, go vet, go build, go test, 미구현 본문(`panic("not implemented")` 등) 없음,
   `unsafe` 사용마다 `SAFETY:` 주석. `-app`과 `-base`를 주면 기록 재생도 포함.
   - 이 저장소 자신에 대해 통과, 미구현·근거 없는 unsafe를 심은 모듈은 실패.
3. **fuzz**: 시드로 재현 가능한 새 입력(한글, 이모지, 제로폭 문자, 긴 입력, NUL 등)을 원본과 재작성에 동시에 넣는다.
   - 동일 재작성 0건, 비ASCII에서만 틀린 재작성은 해당 입력을 찾아냄.
4. **DB 초기화/덤프**: `-db-reset <file.sql>`은 케이스마다 실행되며 `-allow-db-write` 없이는 거부된다.
   초기화로 생긴 변화는 효과에서 제외된다. `-db-dump`는 최종 상태를 JSON으로 저장.
   - SQLite와 PostgreSQL(다중 문장 스크립트) 모두 테스트 통과.
5. **lift**: 앱 재생 전부 통과, 모든 단위가 기록과 일치하고 드리프트 없음, gate 통과일 때만 준비 완료.
   차단 사유를 모두 나열한다. `-original`과 `-base`가 같으면 차단.
   - 실서버로 준비 완료 / 원본 재생 차단 / 단위 드리프트 차단을 각각 확인.
6. **wire gen (자동)**: 한 명령으로 단위를 붙인다.
   - 단위 파일 생성(`units/<unit>/`), 레지스트리 갱신, `main.go`에 마운트 삽입(표식으로 중복 방지), `go build` 확인.
     빌드가 깨지면 `main.go`를 원본 그대로 되돌린다.
   - `-cases app.json`: 그 단위 경로의 기록을 `cases_test.go`(표 기반 테스트)로 만든다.
   - `-agent "<명령>"`: 외부 코딩 에이전트에 기록된 입출력만 넘겨 `rewrite.go`를 쓰게 하고, `go test`로 확인한다.
     실패하면 테스트 출력을 붙여 다시 시도한다(`-attempts`). 원본 소스는 프롬프트에 넣지 않는다(클린룸).
   - 기본값은 원본 서비스 응답이고, `GA_UNIT_<NAME>=rewrite`로 재작성을 고른다.
   - 실제 실행(Claude Code 2.1): 기록 4개로 `rewrite.go`를 생성해 테스트 통과. 기록에 없는 입력 17개를 원본과 비교하면
     14개 동일, 3개 다름(`/orders/0`, `/orders/3/`, `/orders/`). 기록이 넓지 않으면 통과가 곧 완성은 아니다.
   - `wire set <routes.json> <unit> <rewrite|original>`: 프론트도어 라우팅을 바꾼다. 재시작 없이 다음 요청부터 반영된다.
   - CLI 단위: `wire gen <모듈> <unit>`(접두사 없음). 명령 이름이 단위 이름이고, `main` 시작부에 `units.RunCLI`를 넣는다.
     원본은 `GA_ORIGINAL_CLI`로 지정한 실행 파일을 같은 인자·입력으로 호출한다. `GA_UNIT_<NAME>=rewrite`로 재작성을 고른다.
     기록의 CLI 케이스(인자, stdin, 종료 코드, 출력)가 `cases_test.go`가 된다.
     실제 실행(Claude Code): 기록 5개에 대해 재작성이 테스트를 통과. 기록에 없는 입력 14개 중 10개 동일, 4개 다름
     (`-1`, `+5`, `" 9 "`, 아주 큰 숫자). 에이전트가 근거 없이 정한 가장자리 규칙이 원인이다.
   - `wire refine <모듈> <unit> -cases app.json (-original-cli BIN | -original-url URL) [-agent CMD]`: 루프.
     임의 입력(경계값, 생성 입력, CLI는 인자와 stdin 두 형태)을 원본과 재작성에 넣고, 응답이 다른 입력은
     원본의 응답을 정답으로 기록에 추가한다. 테스트를 다시 만들고 에이전트가 재작성을 고친다. 차이가 0이 될 때 수렴한다.
     실제 실행(Claude Code): 기록 5개에서 시작해 2라운드에 7개, 3라운드에 1개 차이를 찾아 기록했고, 이후
     새 입력 120개에서 차이 0으로 수렴했다. 이전 차이 입력 22개도 원본과 모두 같다(도구 밖 손 검증).
     HTTP 단위도 같은 방식으로 실제 에이전트에 돌렸다. 기록 4개에서 시작해 끝 슬래시 형태를 프로브에 추가한 뒤
     3라운드에 수렴했다. 실제 HTTP 서버 비교에서 `/orders/` 안의 25개 중 24개가 같았다. 남은 1개(`/orders//1`)는
     앱의 `ServeMux`가 경로를 정리해 301로 돌려보내서 생긴 차이이며, 단위 자체가 아니다.
   - 프로브는 값과 경로 모양(끝 슬래시)을 바꾼다. `//`처럼 앱 라우터가 먼저 처리하는 경로는 단위에 닿지 않는다.
   - 한계: 수렴은 시도한 입력 범위 안에서의 일치다. 원본에 존재하는 다른 입력(예: 101~499 구간의 실제 주문)은 시도되지 않으면 모른다.
     에이전트가 자기 테스트를 실행하지 못하는 경우가 있어, 최종 확인은 도구가 한다(RunAgent의 go test, refine의 재탐색).

## 전체 검증
- `go vet ./...` 통과, `go test -race -count=1 ./...` 302개 통과(퍼즈 시드 포함), 실패 0.
- PostgreSQL 테스트 9개는 `GA_TEST_PG_ADMIN_DSN`이 있을 때만 실행된다. 이번 라운드에서 PostgreSQL 17 일회용 컨테이너로 통과를 확인한 뒤 제거했다.
- 자기 자신에 대한 `go-anything gate`는 통과.

## 알려진 한계 (숨기지 않음)
- **lift**는 재작성이 내부에서 원본을 호출하는지 증명하지 못한다. 이 점은 출력에도 명시되어 있다.
- **wire**: `wire gen`은 코드를 생성하지만 rust-anything처럼 빌드·재생·원본 기록까지 자동으로 하지 않는다. `wire set`은 라우팅 전환이다.
- **비결정성**은 `-repeat` 횟수 안에서 드러난 차이만 잡는다. 드물게만 달라지는 값은 놓칠 수 있다.
- **fuzz**는 입력 생성기의 조각 목록 범위 안에서만 탐색한다. 생성기가 다루지 않는 입력은 찾지 못한다.
- **db-reset**은 사용자가 준 스크립트를 그대로 실행한다. 권한 있는 DB 계정을 쓰면 운영 데이터를 지울 수 있으므로 반드시 격리된 데이터베이스에서만 써야 한다.
- **gate의 unsafe 검사**는 텍스트 기준이다. 주석과 문자열 속 `unsafe.`은 대부분 걸러지지만, 정교한 구문 분석은 아니다.
- 요청 헤더 전송(인증 토큰), 메일(SMTP) 효과, MCP 도구 확장, analyze 심화, shadow 모듈 생성은 이번 범위(1~6)에 포함되지 않아 여전히 미구현이다.
- gate의 미구현 검사와 unsafe 검사는 구문 트리 기준이다. 템플릿 문자열 안의 글자는 코드로 보지 않는다.
